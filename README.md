## 项目简介

本技能是一个面向 AI Agent 平台（WorkBuddy、Claude Code、Codex 等支持 SKILL.md 规范的平台）的公文写作能力包。它解决的是一条很具体的业务链路上的问题：**在国企内部用 AI 起草和排版公文时，既不能让企业敏感信息流出，又要保证成品在字体、字号、行距、缩进、页码上经得起逐字检查。**

适用对象：

| 对象 | 典型诉求 |
| --- | --- |
| 文秘与综合管理岗 | 起草请示、通知、函、总结、纪要、报告，要求格式规范 |
| 制度编制岗 | 起草办法、规定、细则、操作规程、工作指引，要求体例合规矩 |
| 财务与业务部门 | 向集团报送报告、方案，既要写得好又要排得对 |
| 审核岗 | 检查已有公文哪里不规范，逐项给出修改意见 |

设计理念一句话概括：**规范要什么就给什么，不用差不多兜底。** 字体名、字号、行距、缩进、页码位置全部咬死到字面值；本机缺什么字体就如实说明并给出方案，绝不默默降级替换。

## 解决什么问题

### 痛点一 敏感信息不能外流

公文里天然含大量敏感信息：企业内部名称、经办人手机号、身份证号、银行账号、合同金额。直接丢给 AI 处理等于泄露。本技能在**写作之前**就把这些内容替换成占位符，AI 全程只看得到占位符，产出后再把原始值还原回去。全程可逆，用户拿到的成品与原文一致。

### 痛点二 公文写作格式不规范

「格式不规范」其实是两件事，一件关乎语言，一件关乎版式，AI 写作时两头都容易失守。

**第一个层面 语言不规范。** 通用大模型的语言底子是新闻体与评论体，产出的句子读着通顺，却不是公文该有的样子：口语词（老百姓、一把手、打算）随手就写；语气不分上下（对上级用「要求」而非「拟请」）；数字与纪年混用（写成二〇〇六年、上世纪八十年代）；句子成分残缺（「通过学习，使全体干部提高了认识」缺主语）。单看一处不起眼，通篇累积就失了公文的体面。

**第二个层面 格式不规范。** GB/T 9704-2012 对公文版式有几十项硬性要求：字体字号、行距、缩进、页边距、层次序数、页码编排、发文字号，一项都不能错；制度类文件用的又是另一套体例与版式参数。这些细节量大、琐碎、易忘，靠人脑记忆无法保证每次都准。

### 痛点三 成品看着对细究错

用 python-docx 生成 docx 有一个隐蔽的陷阱：**API 返回成功不等于 Word 里正确。** 例如样式里残留的主题字体属性优先级高于显式字体名，会导致文件里写着仿宋_GB2312 而 Word 实际渲染成等线；页边距写成 `sectPr` 的子元素而非 `pgMar` 的属性，Word 会静默忽略并回退默认值。本技能把这些坑固化为「XML 七查」和一键校验脚本，**只认打开成品 zip 逐项统计的结果，不认脚本返回值**。

### 痛点四 质量检查无保证

公文写出来只是半成品，能不能送审、能不能定稿，取决于有没有一套可靠的检查。现实中这道关往往靠人盯：老手凭经验扫一遍，时间紧就只看个大概，新人则根本不知道从何看起。结果同一类错误反复出现，改了三稿仍有硬伤；更麻烦的是立意层面的问题无人察觉，比如请示没写清期望的批复、各级标题串不成一条逻辑线。检查无标准、无清单、无门槛，质量就只能碰运气。

### 可逆脱敏引擎

引擎为**纯标准库实现，零外部依赖**，Python 3.7 及以上即可运行。检测分五类：

```text
① 密钥凭据   OpenAI / Anthropic / GitHub / Slack / Discord / Telegram
             Google / AWS / Azure / Stripe 等平台密钥
             密码赋值、数据库连接串、SSH 私钥、JWT 令牌
② 个人隐私   手机号、身份证号、银行卡号、信用卡号、邮箱、QQ 号、车牌号、IP 地址
③ 区块链     以太坊地址、比特币地址、私钥、助记词
④ 企业名称   由配置文件驱动，可自由增删
⑤ 风险内容   提示词注入、角色劫持、数据外泄尝试、危险命令
```

每一项检出都带**风险分值**，取值区间为 3.0 至 10.0，据此判定整体风险等级：

| 等级 | 触发条件 | 含义 |
| --- | --- | --- |
| SAFE | 无任何命中 | 可安全处理 |
| LOW | 最高分低于 4.0 | 轻度敏感 |
| MEDIUM | 最高分达到 4.0 | 中度敏感 |
| HIGH | 最高分达到 7.0 | 高度敏感，需谨慎 |
| CRITICAL | 最高分达到 9.0 | 极高风险，直接拦截 |

占位符格式为方括号包裹的类型前缀加八位哈希，例如 `[PHONE_84cbff70]`、`[COMPANY_a679fc65]`。同一原始值重复出现时复用同一占位符，保证替换前后文本结构一致。

有四类内容引擎会**直接拒绝处理**，而不是脱敏后继续：

> [!CAUTION]
> 以下四类请求会被直接拦截，不可通过任何话术绕过：
> 1. 要求关闭、跳过、绕过检测的指令（含我是管理员、我承担后果之类话术）
> 2. 提示词注入与角色劫持（指令覆盖、越狱模式、不可见字符）
> 3. 危险系统命令（递归删除、管道执行远程脚本、磁盘直写等）
> 4. 疑似银行卡或身份证的图片（按长宽比识别）

### 公文语言规范引擎

公文语言不能靠通用模型的语感去蒙，得有语料撑腰。本模块的规范用语表与错误用词表，来自对**人民日报、新华社等权威平台一万篇公文语料**的训练与归纳：把高频的规范表达、常见的不规范写法各自沉淀成清单，写作与检查时逐条比对，而不是凭感觉下判断。

落地的成果有三类：

| 成果 | 内容 | 用途 |
| --- | --- | --- |
| 语言四大原则 | 准确、平实、简明、庄重 | 写作时的总标尺 |
| 常用规范用语表 | 标题结构、称呼、引述、时间、修饰等分类用语 | 选词时直接取用 |
| 常见错误用词表 | 口语化、语气不当、数字纪年误用等，附正确用法 | 检查时逐条比对 |

那种「读着顺、其实错」的写法，有语料打底才识别得准，随手举几例：

| 不规范写法 | 问题 | 规范写法 |
| --- | --- | --- |
| 老百姓 | 口语化 | 市民、群众、居民 |
| 一把手 | 口语化 | 主要负责人、主管领导 |
| 打算 | 口语化 | 决定、拟定、计划 |
| 狠抓 | 口语感强 | 强化、加强、加大力度 |
| 要求（对上级） | 语气强硬 | 拟请、恳请、建议 |
| 截止2014年10月30日 | 截止后不能直接跟时间 | 截至2014年10月30日 |
| 上世纪八十年代以来 | 世纪年代应用阿拉伯数字 | 20世纪80年代以来 |

### 公文格式规范

覆盖 GB/T 9704-2012 的版面、字体、层次序数、页码编排、发文字号、成文日期等全部要素，并额外固化了**本单位的实操口径**，详见[格式规范速查](#格式规范速查)。

内置六类常用文种模板：请示、通知、函、总结、会议纪要、报告。每类均附使用场景、结构骨架、写作要点与真实案例。

### 制度类文件规范

适用于名称含制度、办法、规定、细则、规范、清单、政策、操作规程、实施细则、工作指引的内部文件。这部分与公文**体例完全不同**，是本技能相对通用公文助手的最大差异点：

| 维度 | 要点 |
| --- | --- |
| 两套体例 | 内容丰富走分章贯条式，内容简短走条文到底式 |
| 六层序数 | 第X章 → 第X节 → 第X条 → 款 → （一）项 → 1. 目 |
| 六要素骨架 | 目的依据、适用范围定义、体制职责、管理内容流程、解释部门、施行日期 |
| 硬约束一 | 全文不得出现公文体「一、」式一级标题 |
| 硬约束二 | 条号必须全文大流水连续，不按章重新起算 |

### 文档生成与校验

生成器可按实测版式参数**一次成稿**，生成即自动清理主题字体、主题色、自动间距、段落边框与内置蓝值。校验器则是**公文与制度双档校验器**，逐项统计并给出 PASS 或 FAIL 判定。

### 质量检查清单

清单共 100 余项，分九章。最具特色的是**第〇章「钟主任定稿前九问」门槛**：九问不是检查项而是归零项，任何一问答不上来即视为未达送审程度，须回炉重写。检查顺序强制为**先九问、再内容、后技术**，顺序不可颠倒。

**为什么把九问顶在最前面。** 常规检查盯的是字词、标点、格式这些「表面合格」；九问盯的是「这篇公文立不立得住」：第一句是不是结论、小标题撑不撑得住下面的内容、删掉一句会不会影响决策、请示有没有写清期望的批复。立意不成立，格式再规范也是白查。所以九问是**门槛**，不是加分项，答不上来就回炉，不与后面的检查并行。

九问取自公文写作专家钟主任的审稿法，是本技能区别于通用写作助手的一项标志性内容，清单正文第〇章即为其完整展开。

## 工作原理

每次处理公文时，技能自动执行脱敏、写作、还原三步，用户无感知。

```text
                    ┌──────────────────────────┐
                    │   用户提供公文或素材       │
                    └────────────┬─────────────┘
                                 │
                                 v
        ┌────────────────────────────────────────────────┐
        │  第 1 步  可逆脱敏                              │
        │  process_user_message()  或  process_file()    │
        │  敏感信息 ──▶ [PHONE_xxx] [COMPANY_xxx] 等占位符 │
        └────────────────────┬───────────────────────────┘
                             │  脱敏后的文本
                             v
        ┌────────────────────────────────────────────────┐
        │  第 2 步  公文写作、润色、排版                   │
        │  在脱敏文本上执行格式处理与语言加工              │
        │  AI 全程只见占位符，接触不到真实信息             │
        └────────────────────┬───────────────────────────┘
                             │  加工后的脱敏文本
                             v
        ┌────────────────────────────────────────────────┐
        │  第 3 步  还原敏感信息                          │
        │  restore_ai_response()                         │
        │  占位符 ──▶ 原始值                              │
        └────────────────────┬───────────────────────────┘
                             │
                             v
                    ┌──────────────────────────┐
                    │   返回完整成品给用户       │
                    └──────────────────────────┘
```

引擎的核心接口：

| 接口 | 用途 | 调用时机 |
| --- | --- | --- |
| `process_user_message(msg)` | 脱敏用户消息 | 收到公文内容后的第一步 |
| `process_file(path)` | 脱敏文件内容 | 处理用户上传的文本类文件 |
| `restore_ai_response(text)` | 还原占位符 | 返回结果给用户前的最后一步 |
| `scan_text(text)` | 只扫描不修改，返回风险等级 | 需要先评估风险时 |
| `health_check()` | 引擎自检，返回通过率 | 排查脱敏是否正常工作 |

映射关系落盘在 `sensitive_mappings.json`，键为占位符、值为原始内容。该文件属**运行时产物**，每次脱敏都会重写，已在版本库中排除。

## 安装部署

### 环境要求

| 项目 | 要求 | 说明 |
| --- | --- | --- |
| Python | 3.7 及以上 | 脱敏引擎与校验器零外部依赖 |
| python-docx | 仅生成与自检需要 | 脱敏引擎与校验器不需要 |
| 中文字体 | 建议按规范安装 | 详见下方字体说明 |
| 操作系统 | 跨平台 | 脱敏引擎兼容 Windows、macOS、Linux |

### 安装技能

把整个目录放入平台的技能目录即可。用户级安装对当前账号下所有项目生效：

```bash
git clone https://github.com/OwenZhou24/huazhong-gongwen-1.5.git \
  ~/.workbuddy/skills/huazhong-gongwen-1.5
```

项目级安装只对单个项目生效：

```bash
git clone https://github.com/OwenZhou24/huazhong-gongwen-1.5.git \
  <你的项目>/.workbuddy/skills/huazhong-gongwen-1.5
```

> [!NOTE]
> 目录名可以任意修改。平台通过 `SKILL.md` 头部的 `name` 与 `description` 字段识别技能，不依赖文件夹名。

### 安装依赖

只有生成器和自检脚本需要 `python-docx`：

```bash
python -m pip install python-docx
```

### 字体说明

规范要求的字体中，**方正小标宋简体并非 Windows 系统自带**。生成文档前请先确认本机是否安装：

```text
需核查的字体清单
  黑体                 通常系统自带
  仿宋_GB2312          通常随 Office 安装
  楷体_GB2312          通常随 Office 安装
  Times New Roman      系统自带
  方正小标宋简体        需单独安装，系统不自带
```

> [!IMPORTANT]
> 若本机缺少方正小标宋简体，生成的文件内仍会写入该字体名，以保证在单位电脑上正确呈现。请在交付说明中提示使用者安装该字体，**不要默默替换成宋体加粗之类**。

### 首次使用

首次运行时引擎会自动创建映射表文件，无需手工干预。想验证安装是否完好，直接跑一次自检：

```bash
python scripts/selfcheck.py
```

## 快速开始

### 场景一 起草一份请示

```text
用户：帮我写一份关于申请增加信息化建设预算的请示，报集团
```

技能的执行路径：

1. 先对用户输入执行脱敏，识别其中的企业名与人名
2. 询问要素：请示事由、主送机关、金额、依据
3. 加载 `@references/document-templates.md` 中的请示模板生成骨架
4. 按公文语言规范撰写正文，一级标题用「一、」黑体三号
5. 用 `@checklists/quality-checklist.md` 逐项核对
6. 还原占位符，输出完整公文

产出：格式规范的正文，可直接粘贴进 Word 或交给排版脚本处理。

### 场景二 检查一份公文哪里不规范

```text
用户：帮我看看这份通知的格式有没有问题（附正文）
```

技能的执行路径：

1. 脱敏后通读全文
2. 先过第〇章九问，判断是否达到送审程度
3. 再过第二章内容检查，核对通知要素是否齐备
4. 最后过格式、语言、逻辑、细节各章做技术性收尾
5. 逐条列出问题，标注位置并给出正确写法

产出：一份带定位与修改建议的问题清单。

### 场景三 起草一份管理办法

```text
用户：帮我起草一份资产管理办法，含总则、职责、日常管理、处置和附则
```

技能的执行路径：

1. 判定体例：内容较丰富，走分章贯条式
2. 搭骨架：总则、职责章、中间各业务章、附则
3. 核对六要素是否齐备
4. 按制度类六层序数写作，条号大流水编号
5. 用 `@scripts/build_zhidu_docx.py` 一次成稿
6. 用 `@scripts/verify_docx.py` 按制度档校验

产出：排版合规的 docx 文件，直接可用。

### 场景四 直接生成制度类 docx

准备好带标记的纯文本，一行命令成稿：

```bash
python scripts/build_zhidu_docx.py 输入.txt 输出.docx
```

输入文本的行首标记约定：

| 标记 | 含义 | 排版效果 |
| --- | --- | --- |
| `T\|` | 文件标题行 | 居中，方正小标宋简体二号 |
| `C\|` | 副题，如征求意见稿 | 居中，楷体三号 |
| `Z\|` | 章 | 黑体三号居中，序号后两个半角空格 |
| `J\|` | 节 | 仿宋_GB2312 三号加粗居中 |
| 第X条 | 条 | 条号加粗加条文仿宋，首行缩进两字符 |
| 其他任意行 | 款、项、目、正文 | 仿宋_GB2312 三号，首行缩进两字符 |

示例输入：

```text
T|HD融资担保股份有限公司
T|XXXX管理办法
C|（征求意见稿）
Z|第一章  总则
第一条  为规范……，根据……，结合公司实际，制定本办法。
第二条  本办法适用于公司及各子公司。
Z|第二章  附则
第三条  本办法由公司综合管理部负责解释。
第四条  本办法自印发之日起施行。
```

## 配置说明

### 企业名称清单

需要检测的企业名称写在 `@config/company_names.json` 中，直接编辑即可增删，**修改后无需重启，下次匹配自动生效**：

```json
{
  "description": "企业敏感名称列表 — 在此文件中添加或删除需要检测的企业名称",
  "note": "修改后无需重启，下次匹配自动生效",
  "company_names": [
    "示例担保",
    "示例（城市）融资担保股份有限公司",
    "示例金融控股集团"
  ]
}
```

引擎按**名称长度降序**匹配并做区间去重，因此同时配置简称与全称时优先命中较长的全称，不会出现长名称被简称截断的情况。

### 脱敏映射表

`sensitive_mappings.json` 由引擎在运行时自动创建与维护，记录占位符与原始值的对应关系。**该文件已加入 `.gitignore`，请勿提交到版本库**：它每次脱敏都会重写，且内容本身就是敏感信息。

### 转为公开仓库前必做

本仓库的 `company_names.json` 含企业内部真实名称。若要将仓库转为公开，必须先把清单替换为脱敏模板：

```bash
cp config/company_names.example.json config/company_names.json
git add -A
git commit -m "脱敏：替换企业名单为示例值"
git push
```

> [!WARNING]
> 仅替换当前文件**不足以彻底清除**，历史提交中仍保留真实名称。转公开前还需重写提交历史（例如使用 git filter-repo 工具），否则任何人翻看历史记录都能看到原始清单。

## 命令行工具

### 包自检 selfcheck

一次运行复验全部环节是否完好、引用是否到位。

```bash
python scripts/selfcheck.py                 # 自检本脚本所在技能包
python scripts/selfcheck.py --pkg <目录>     # 指定其它技能包
python scripts/selfcheck.py --deep          # 追加反向缺陷注入验证
```

| 参数 | 说明 |
| --- | --- |
| `--pkg` | 技能包根目录，默认取脚本的上级目录 |
| `--deep` | 追加反向验证：故意注入缺陷，确认校验器真能报错 |

十项检查内容：

| 编号 | 检查项 | 判据 |
| --- | --- | --- |
| 1 | 必需文件完整性 | 核心文件全部就位 |
| 2 | SKILL.md frontmatter | 含 name 与 description 字段 |
| 2b | 引用强制读取规则 | 硬指令块与关键措辞齐备 |
| 3 | 目录与行内锚点 | 全包 markdown 锚点全部有效 |
| 4 | 全包引用解析 | @ 引用全部命中，无残留本地链接 |
| 5 | 正文半角引号 | 代码区豁免后无半角引号，围栏成对 |
| 6 | Python 语法编译 | 全部 .py 编译通过 |
| 7 | 脱敏还原往返 | 占位符替换后能原样还原 |
| 8 | 制度类生成与校验 | 生成 docx 并通过制度档校验 |
| 9 | 公文档分支可运行 | 默认档校验分支正常 |
| 10 | 反向缺陷注入 | 仅 `--deep` 时执行 |

> [!TIP]
> 运行类检查一律在**临时克隆目录**中进行，不会污染本包的映射表文件。

### docx 校验器 verify_docx

对生成的 docx 做逐项技术核查，输出计数与 PASS 或 FAIL 判定。

```bash
python scripts/verify_docx.py 成品.docx                # 默认按公文档校验
python scripts/verify_docx.py 成品.docx --type zhidu   # 按制度档校验
```

| 参数 | 说明 |
| --- | --- |
| 位置参数 | 待校验的 docx 路径 |
| `--type` | 取值 `gongwen` 或 `zhidu`，默认 `gongwen` |

两档的期望值差异：

| 校验项 | 公文档 | 制度档 |
| --- | --- | --- |
| 页边距 | 上37 下35 左28 右26 毫米 | 上下各36 左右各27 毫米 |
| 固定行距 | 28 磅 | 30 磅 |
| 页码 | 单页居右双页居左，奇偶不同 | 页脚居中，无奇偶差异 |
| 段落边框 | 必须为 0 | 必须为 0 |
| 主题字体与主题色 | 必须为 0 | 必须为 0 |

校验器覆盖的七项核心检查：

```text
[1] 主题字体残留      w:asciiTheme / hAnsiTheme / eastAsiaTheme / cstheme
[2] 主题颜色残留      w:themeColor / themeShade / themeTint / themeFill 系列
[3] 自动间距残留      w:beforeAutospacing / w:afterAutospacing
[4] 段落边框与内置蓝  w:pBdr 与 Word 内置蓝色值
[5] pPr 子元素顺序    OOXML 要求严格有序，顺序错则 Word 静默忽略属性
[6] 段落级显式落地    每段逐段含缩进、固定行距、对齐；每 run 含字体字号
[7] 制度类专项        行距取值、页边距、章节标题居中且清零缩进、条号后两空格
```

> [!WARNING]
> 校验必须以**打开成品 zip 逐项统计**的结果为准。只看生成脚本的返回值即为假过。本项目初版曾因校验脚本与生成代码犯同一个错误（都从 `sectPr` 直子读页边距，而非从 `pgMar` 属性读），导致页边距实际错误却双双报 PASS。

### 制度类生成器 build_zhidu_docx

```bash
python scripts/build_zhidu_docx.py <输入.txt> <输出.docx>
```

生成时自动完成的处理：

- 按实测版式参数设定 A4 页面、页边距、固定值 30 磅行距、段前段后归零
- 章标题黑体三号居中，并显式清零首行缩进
- 节标题仿宋_GB2312 三号加粗居中
- 条号与条文分别设定字体，序号后统一补两个半角空格
- 章名附则两字之间补足两个半角空格
- 页脚插入页码域，呈居中一字线包围形式
- 全包清理主题字体、主题色、自动间距、段落边框与内置蓝值

### 脱敏引擎 sensitive_detector

可直接运行查看演示与自检结果：

```bash
python sensitive_detector.py
```

输出包含三部分：脱敏示例、安全拦截演示、引擎健康自检通过率。

## 格式规范速查

### 公文版式参数

| 要素 | 规格 |
| --- | --- |
| 用纸 | A4，210 毫米乘 297 毫米 |
| 天头（上白边） | 37 毫米 |
| 订口（左白边） | 28 毫米 |
| 版心 | 156 毫米乘 225 毫米 |
| 行距 | 28 磅 |
| 每面容量 | 22 行，每行 28 字 |

### 公文与制度类字体字号对照

| 要素 | 公文类 | 制度类 |
| --- | --- | --- |
| 文件标题 | 小标宋体 二号 居中 | 方正小标宋简体 二号 居中 |
| 章标题 | 无此层级 | 黑体 三号 居中 |
| 节标题 | 无此层级 | 仿宋_GB2312 三号 加粗 居中 |
| 一级层次 | 黑体 三号，形如一、 | 无一级层次式样，一级即章 |
| 二级层次 | 楷体_GB2312 三号，形如（一） | 第X条，条号仿宋加粗 |
| 正文 | 仿宋_GB2312 三号 | 仿宋_GB2312 三号 |
| 发文字号 | 仿宋_GB2312 三号，六角括号 | 不设 |
| 页码 | 宋体 四号 半角，单右双左 | 宋体 四号，页脚居中 |
| 西文与数字 | Times New Roman | Times New Roman |

### 层次序数对照

```text
公文类 四层                          制度类 六层
  一、       黑体三号                  第X章  章名     黑体三号居中
  （一）     楷体_GB2312 三号           第X节  节名     仿宋加粗居中
    1.       仿宋_GB2312 三号            第X条  ……       条号加粗，大流水编号
      （1）  仿宋_GB2312 三号            款 不编号，另起自然段
                                        （一）项          中文数字加括号
                                         1. 目            阿拉伯数字加下脚点
```

### 缩进与对齐口径

本单位规范与国标默认略有差异，**以本单位口径为准**：

| 项目 | 口径 |
| --- | --- |
| 正文 | 两端对齐，首行缩进 2 字符 |
| 各级层次标题 | 与正文一致，两端对齐，首行缩进 2 字符 |
| 文件标题、发文机关标志 | 居中 |
| 主送机关 | 顶格，无首行缩进，后接全角冒号 |
| 落款、成文日期 | 居右，右空四字编排 |
| 制度类章标题 | 居中，且须显式清零首行缩进 |

实现要点：缩进必须写成**字符单位**的属性，取值 200 表示 2 字符。使用固定长度单位（磅或 twips）的写法不会随字号自适应，属错误实现。校验判据是文档中左对齐的计数必须为 0。

### 页码编排

| 项目 | 要求 |
| --- | --- |
| 字体字号 | 四号半角宋体阿拉伯数字 |
| 位置 | 版心下边缘之下，一字线上距版心下边缘 7 毫米 |
| 奇偶 | 单页码居右空一字，双页码居左空一字 |
| 装饰 | 数字左右各一条一字线，形如一 1 一 |
| 实现 | 页脚插入页码域，页脚距页底 28 毫米 |

## 质量检查体系

检查清单共九章，**使用顺序强制固定**：

```text
第〇章  钟主任九问          定稿门槛，九问全过才进入下一步
第二章  内容检查清单        按文种核对要素齐备性
第一 / 三 / 四 / 五 / 六章   格式、语言、逻辑、细节、发文前技术性收尾
第八章  制度类专项检查       制度类文件改走此章，跳过公文特有项目
第九章  常规公文必查 20 项   时间紧时与九问配合使用的速查表
```

### 定稿门槛 钟主任定稿前九问

九问来自公文写作专家钟主任的审稿法，是本技能最具标志性的一项特色。它不是检查项而是**归零项**：任何一问答不上来或答否，即视为未达送审程度，须回炉重写后再答。

```text
问1  第一句话是结论吗，三十秒内能抓住判断吗
问2  每个小标题下面的内容，都能支撑它吗
问3  信息分组了吗，同一组里是同一类事吗
问4  每组的排序逻辑说得出吗，全文有没有乱跳
问5  删掉任何一句，会影响读者决策吗
问6  关键判断后面，跟着数字和论据吗
问7  各级标题连起来读，是一篇摘要吗
问8  请示写清了事项、依据和期望的批复了吗
问9  篇幅还能再压三分之一吗
```

### 各章检查项分布

| 章节 | 检查项规模 | 覆盖内容 |
| --- | --- | --- |
| 第一章 格式检查 | 40 余项 | 用纸版面、字体字号、缩进对齐、层次序数、日期文号 |
| 第二章 内容检查 | 30 余项 | 标题、主送机关、正文要素、结尾用语、附件 |
| 第三章 语言检查 | 40 余项 | 四大原则、常见错误用词、规范用语、口语化 |
| 第四章 逻辑检查 | 10 余项 | 层次结构、内容一致性、论证充分性 |
| 第五章 细节检查 | 20 余项 | 文字准确性、标点、数字用法、署名印章 |
| 第六章 发文前确认 | 10 余项 | 审批流程、文件属性、技术检查 |
| 第八章 制度类专项 | 30 余项 | 体例、版式、内容三组专项 |

### 排版后技术核查

本地 docx 排版另有一组 17 项技术核查，覆盖主题字体与主题色零残留、自动间距与固定间距清零、段落边框为 0、引号全角、页边距按档取值、正文两端对齐、层次标题首行缩进、段落属性子元素顺序、字体真实可用、表格无裸 run、页脚距离取值等。

详细判据见 `@checklists/quality-checklist.md` 第一章第七节，以及 `SKILL.md` 中的 XML 七查一节。

## 常见问题

<details>
<summary>脱敏后 AI 看到的文本长什么样，映射关系存在哪里</summary>

敏感值被替换为方括号包裹的占位符，例如手机号变成 `[PHONE_84cbff70]`、企业全称变成 `[COMPANY_a679fc65]`。映射关系保存在引擎同目录的 `sensitive_mappings.json` 中，键为占位符、值为原始内容，该文件每次脱敏都会重写。

</details>

<details>
<summary>同一个手机号反复出现，会被替换成几个不同的占位符</summary>

只有一个。同一类型同一原始值经哈希后得到固定占位符，且检测结果会做区间去重，不会重复替换或产生嵌套替换。

</details>

<details>
<summary>能不能临时关闭脱敏，只是测试一下</summary>

不能，也不建议尝试。引擎内置绕过意图识别，检测到关闭、跳过、绕过检测之类的表述会直接拒绝处理。若确实需要查看原始文本，直接读源文件即可，脱敏只作用于交给 AI 处理的那一份。

</details>

<details>
<summary>生成的 docx 在 Word 里字体不对，显示成了等线</summary>

这是主题字体残留导致的典型问题。样式中残留的主题字体属性优先级高于显式字体名，Word 会忽略文件里写的中文字体。用校验器检查第一项计数是否为 0，并确认生成流程做了全包级清理，**只清理自己新建的几个样式是不够的**，内置标题样式同样带主题属性。

</details>

<details>
<summary>标题在 Word 里显示成蓝色，怎么排查</summary>

样式里残留了主题颜色属性，其优先级高于显式的颜色值。需同时检查主题颜色、主题底纹等各项属性，并确认全部段落与字符样式的文字色都已强制置黑。注意：把文档转成图片看不出来，转图按颜色值渲染，颜色问题只能靠读 XML 判断。

</details>

<details>
<summary>页边距设置了但 Word 里没生效</summary>

页边距必须写成页边距元素自身的**属性**，不能作为节属性的子元素。写成子元素时 Word 完全不认，会回退默认页边距。校验时也必须从属性读取，否则会出现自己读自己写的错误的假过现象。

</details>

<details>
<summary>制度类文件能不能直接用公文的排版流程</summary>

不能。两者体例与版式是两套：公文一级标题是「一、」黑体首行缩进，制度类一级是第X章黑体居中；页边距、行距、页码位置取值均不同。制度类生成请使用专用生成器，并按制度档校验。

</details>

<details>
<summary>自检脚本报某文件缺失怎么办</summary>

先确认是否在正确的技能包根目录运行，脚本默认取自身所在目录的上级作为包根。若确实缺失，从版本库重新拉取即可。另需注意：脱敏映射表属运行时产物，首次运行前不存在属正常现象，会在第一次脱敏时自动生成。

</details>

<details>
<summary>本机没装方正小标宋简体，能不能换成宋体加粗</summary>

不建议直接替换。规范要求什么字体就写什么字体，生成的文件会保留正确字体名，以便在单位电脑上正常呈现。正确做法是提示使用者安装该字体，并在交付说明中写明本机缺失情况，而不是默默降级。

</details>

<details>
<summary>这个技能支持哪些平台</summary>

凡支持 SKILL.md 规范的 Agent 平台均可加载，包括 WorkBuddy、Claude Code、Codex 等。技能包本身不依赖任何平台专有接口，核心能力由 `SKILL.md` 的指令与独立 Python 脚本提供。

</details>
